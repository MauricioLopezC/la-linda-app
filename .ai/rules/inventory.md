# Inventory

## Stock: quantities are decimal, the sign lives in the movement line
Settled while building the HU-016/017/018 schema, revised in the HU-017 stock-movement redesign:

- Quantities are `decimal(12, 3)`, cast `decimal:3`, not integers: the catalog seeds Kilogramo and Litro as units of measure, so bulk articles need fractional stock.
- `stock_movement_items.quantity` is a **signed delta** (negative leaves the warehouse, positive enters) and is the stored source of truth for the sign of a line. Balances are recomputed from this column, never from `stock_movement_types.sign`. `system_quantity` is an informative snapshot of the balance right before the line was applied (audit trail / future running balance) — never an input, never typed by the user, not shown on the create screen.
- `stock_balances` has no HTTP write route. The quantity only changes as a consequence of a `StockMovement`, inside a transaction. The read-only UI of HU-016 is a consequence of that, not a UI rule.
- `StockMovement` is immutable: no `updated_at` column, `const UPDATED_AT = null`, and no update/delete route. `created_at` is the date of the movement.
- One movement row = one affected warehouse. A transfer is two rows (types `warehouse_transfer_out` / `warehouse_transfer_in`); the column that groups them is deliberately absent until HU-019 brings the `stock_transfers` header. Tell movement kinds apart by `stock_movement_types.code` only.
- There is no `stock_adjustment_reasons` table. The descriptive "why" of a manual movement lives in the movement type's name (`breakage`, `expiration`, `count_shortage`, …), an admin-managed catalog (HU-031). `notes` on the header is required for manual movements as the free-text justification.

## stock_movement_types.sign: fixed per type, derives the delta once on write
`sign` is `NOT NULL` for every type — `1` (suma / enters) or `-1` (resta / leaves). There is no "varies per line" state.

- On a manual movement, `RegisterStockAdjustment` derives each line's delta **once** as `type.sign * quantity`, where `quantity` is the positive amount the user typed. After that, balances are always recomputed from the stored `stock_movement_items.quantity`, never from `type.sign` — the type is user-editable (`UpdateStockMovementType`, `Store/UpdateStockMovementTypeRequest`), so deriving a balance from it would let editing a type rewrite the meaning of its whole immutable history.
- Changing the sign of a type that already has movements is blocked (`StockMovementType::isInUse()` in `UpdateStockMovementType`; the ABM hides the field via `is_in_use`).
- `StockMovementType::AUTOMATIC_CODES` (`purchase_entry`, `sale_exit`, `customer_return`, `warehouse_transfer_out`, `warehouse_transfer_in`) are generated by other modules and are rejected by the manual-movement action / hidden from its screen (`isAutomatic()`).
- The manual action also rejects any line whose resulting balance would go negative (explicit `ValidationException`; the `stock_balances` `CHECK (quantity >= 0)` is the last-resort net).

Pending, for whoever takes HU-019: the real transfer invariant is that the `out` and `in` lines' deltas sum to zero — enforce it in the transfer action, since the two fixed signs alone don't guarantee equal magnitudes.
